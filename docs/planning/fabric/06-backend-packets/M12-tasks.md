Rulings:
- **DBT-40 first (T2).** Evidence so far: every ledger writer (`app.generate_invoice` 0008/0024, `app.record_payment` 0008/0021) inserts balanced pairs and `tests/db/seed-finance.test.ts` asserts Σdebit = Σcredit in SQL; but `listLedgerEntries`'s `sumQuery` has no `.range()`, so PostgREST `max_rows = 1000` (`supabase/config.toml`) returns an unordered 1,000-row slice of ~25k demo rows. Same cap breaks `termCollectionSummary` (~2,000 invoices/term). T2 confirms in SQL on the demo tenant before fixing; if the SQL books are unbalanced, it stops and reports (then a write path is the bug). **Rule for M12 and after: money aggregates run in SQL (security-invoker functions, RLS applies), never by summing a PostgREST select.**
- **Modules (owner directive 2026-11-02).** `finance.payment.void`, `finance.reminders.send`, `finance.collectionReport` declare `module: "finance_plus"`. `finance.payment.createIntent` declares `module: "online_payments"` (catalogue: requires `finance_plus`). The webhook is not an action: after verifying the signature and loading the intent, it checks `online_payments` for the intent's institution with MOD's enabled-check helper (name per MOD's task file); disabled → 200 `{ ok: true, data: { ignored: "module_disabled" } }`, nothing written. Basic fees (structures, invoices, record payment, receipts, ledger, defaulters, the DBT-40 fix) stay core, no key. Modules are packaging, not a security boundary: permissions + RLS + definer role checks still gate every SQL function, and a direct PostgREST RPC is not module-checked (say so in the 07 §4 row). Risk to record: an ignored webhook is not retried by Razorpay — acceptable in test mode only; live mode (out of scope) must return non-2xx instead.
- **Reversal = new row, never an edit (rule 5).** `payment_reversals`: id, institution_id, `payment_id` unique → payments, invoice_id → invoices, `kind` in (`void`, `refund`, `cheque_bounce`), `amount` numeric(12,2) > 0 (always the full payment amount — partial refunds out of scope), `reason` text 5–500, `snapshot` jsonb = the receipt's `snapshot` plus `reversal: {kind, reason, amount, receipt_no, reversed_at}` (this is the "receipt marked void" snapshot row; `receipts` itself stays untouched), `idempotency_key` text, `reversed_by` → profiles, created_at/updated_at + `set_updated_at` + `app.block_mutation()` (update/delete; has the demo-reset bypass). Unique `(institution_id, idempotency_key)`.
- **`app.void_payment(p_payment_id, p_kind, p_reason, p_idempotency_key)` → jsonb `{reversal_id, invoice_id, invoice_status, paid_total}`**, wrapper `public.void_payment` (same signature, `authenticated` only). Order: load payment → lock its invoice `for update` (same lock as `record_payment`, no deadlock) → idempotent fast path on `(institution, key)` → payment already reversed under another key → `code:conflict` → invoice `cancelled` → `code:invalid_state` → `cheque_bounce` on a non-`cheque` payment → `code:validation_failed` → reason length → `code:validation_failed`. Effects in one transaction: reversal row; ledger Dr `fees_receivable` / Cr `cash` (mode `cash`) or `bank` (other modes) for `amount`, `payment_id` = original, memo `<kind> receipt <no>`, `entry_date` = today in the institution timezone; invoice `paid_total -= amount`, status `issued` when it reaches 0 else `part_paid`. All three kinds post the same entries (refund = money back, fee due again; waiving the fee is invoice cancellation, not M12). Audit `finance.payment.voided` (kind, amount, receipt_no, before/after paid_total + status; never `reason` — free text). Role check in the wrapper: `app.finance_void_roles()` = owner, principal (new, same shape as `app.finance_write_roles()`); caller of another institution → `code:not_found`. No Razorpay refund API call for gateway payments (record only).
- **Fee reminders.** `fee_reminders` log: id, institution_id, invoice_id, student_id, `recipient_user_id` → profiles, `notification_id` → notifications (nullable), `reminder_date` date, `outstanding` numeric(12,2) > 0, created_at/updated_at + trigger; unique `(invoice_id, recipient_user_id, reminder_date)`. Written only by the job handler (service role). `public.enqueue_fee_reminders(p_institution_id, p_term_id)` (definer, `authenticated`): `app.finance_write_roles()`, proves the term belongs to the institution, payload built in SQL `{term_id, as_of}` (as_of = today in institution tz), `app.enqueue_job(..., 'finance.fee_reminder', ..., 'fee_reminders:<term_id>:<as_of>')` — one run per term per day; audits `finance.reminders.enqueued`; return shape mirrors `public.enqueue_term_invoices`. Handler `finance.fee_reminder`: re-reads overdue invoices (term, institution, status `issued`/`part_paid`, `due_on < as_of`, outstanding > 0) paged with `.order("id").range()` in pages of 500 (the max_rows lesson applies to the service role too); recipient = primary guardian (`guardian_students.is_primary`) with an **active** membership; `createNotification` type `fee_reminder`, `entityId` = `<invoice_id>:<as_of>` (one reminder per invoice per recipient per day), contacts from the guardian row; then `fee_reminders` insert `on conflict do nothing`. Re-check state at send (lesson 11). shortcut: one job per term, no chunked continuation — idempotent, so a timed-out run resumes on retry; upgrade when a tenant has > 2,000 defaulters. Automatic daily scheduling is M23 (workflows), not M12.
- **Template `fee_reminder`.** Channels `in_app`, `sms`, `email`; new category `finance` (`NotificationCategory`, `PREFERENCE_CATEGORIES`, and 0074 re-creates `notification_preferences`' category check with `'finance'` added — verify the constraint name from 0068). Vars `{student, invoice_no, amount, due_on, school}` (amount pre-formatted `₹12,345.00`). EN: `Fee reminder: {amount} is due for {student} (invoice {invoice_no}, due {due_on}). Please pay at the school office. -{school}`; HI: `शुल्क अनुस्मारक: {student} के लिए {amount} बकाया है (चालान {invoice_no}, देय तिथि {due_on})। कृपया विद्यालय कार्यालय में भुगतान करें। -{school}`. No "pay online" text (online may be disabled).
- **Collection report.** `public.finance_collection_report(p_institution_id, p_academic_year_id, p_term_id, p_group_by)` plpgsql `stable security invoker`, returns `(group_key text, group_label text, sort_order int, invoice_count bigint, payment_count bigint, billed numeric, collected numeric, reversed numeric, outstanding numeric)`. Scope: non-cancelled invoices of the year (and term if given). `term`/`grade`: billed = Σtotal, collected = Σpaid_total (already net of reversals), reversed = Σ reversal amounts, outstanding = billed − collected, payment_count = unreversed payments; grade via `fee_assignments(student_id, academic_year_id) → fee_structures.grade_id → grades` (finance-owned path, no enrolment read). `mode`: per `payments.mode`, payment_count, collected = Σamount − reversed, reversed, invoice_count = distinct invoices, billed/outstanding null. Bad `p_group_by` → `code:validation_failed`. Order: term sequence, grade order, mode name.
- **Online payments (Razorpay test mode).** `online_payment_intents`: id, institution_id, invoice_id, `amount` numeric(12,2) ≥ 1.00, `currency` = 'INR', `provider` in (`razorpay`, `simulated`), `provider_order_id` text not null unique, `provider_payment_id` text unique, `status` in (`created`, `paid`) (check: `paid` ⇔ payment_id and provider_payment_id not null), `payment_id` unique → payments, `created_by` → profiles, `idempotency_key`, created_at/updated_at + trigger; unique `(institution_id, idempotency_key)`. State machine: `created → paid`, only inside `record_online_payment`; abandoned intents stay `created`. `public.create_payment_intent(p_invoice_id, p_amount, p_provider, p_provider_order_id, p_idempotency_key)` → uuid (definer, `authenticated`): caller holds `app.finance_write_roles()` or is a guardian of the invoice's student, else `code:not_found`; replay key → same id; invoice `issued`/`part_paid` else `code:invalid_state`; 1.00 ≤ amount ≤ outstanding else `code:validation_failed`; order id `^order_[A-Za-z0-9]{6,40}$` for razorpay, `^sim_order_[a-f0-9]{32}$` for simulated; audits `finance.payment.intent_created` (amount, provider). `public.record_online_payment(p_order_id, p_provider_payment_id, p_amount_paise bigint, p_method)` → jsonb `{payment_id, receipt_id, receipt_no, duplicate}` (definer, **`service_role` only**): intent `for update` by order id (none → `code:not_found`); `paid` with the same payment id → existing result, `duplicate: true`; `paid` with another payment id → `code:conflict`; paise ≠ intent amount × 100 → `code:validation_failed`; method `upi`→`upi`, `card`→`card`, else `neft`; calls `app.record_payment(invoice, intent.amount, mode, 'razorpay <pay_id>', now(), 'razorpay:<pay_id>')` (its own outstanding check + `finance.payment.recorded` audit, actor null = system), then marks the intent `paid`.
- **Webhook `POST /api/public/payments/razorpay`.** `RAZORPAY_WEBHOOK_SECRET` unset → 503 `dependency_failed`. Read the raw body as text (cap 64 KB → 413, mirror `readJsonBody`'s cap) and verify `x-razorpay-signature` = hex HMAC-SHA256(raw body, secret) with `timingSafeEqual` **before** `JSON.parse`; bad/missing → 400 `validation_failed`, nothing written. Handled events: `payment.captured`, `order.paid` (payment entity `status = captured`, currency INR); anything else → 200 `ignored: "event"`. Intent looked up by order id via a new service-role factory (`SERVICE_ROLE_CALLER = "payments_webhook"`); institution comes from the intent row, never from payload notes. Error map: `not_found` 404, `validation_failed` 400, `conflict`/`invalid_state` 409, else 500 with correlation id. Never log the body (payer email/phone).
- **Mode + honesty badges (rule 7).** `onlinePaymentsMode()` = `"test"` iff `RAZORPAY_KEY_ID` starts `rzp_test_` and `RAZORPAY_KEY_SECRET` is set; anything else, including a `rzp_live_` key, = `"simulated"` (live keys refused: plan scope is test mode).
