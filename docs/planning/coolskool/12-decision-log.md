# 12 — Decision log

Each ADR: **Decision** · **Context** · **Options** · **Choice and trade-offs** · **Revisit trigger** · **Evidence**. Phase 0 verified facts in §2; debt register in §3. Add new ADRs at the end (D25+); never edit a decision in place — supersede it.

## 1. ADRs

### D1 — Single Next.js App Router app, modular monolith
- **Decision:** one deployable under `src/modules/<domain>/`; no monorepo.
- **Context:** one laptop, 20 days, four parallel lanes, no ops team.
- **Options:** (a) monorepo with packages per domain; (b) separate services (API, worker, web); (c) single app with module folders.
- **Choice:** (c). Trade-off: one build and one dependency graph for everyone; mitigated by file ownership (`09 §3`) and module import rules (`04 §2`).
- **Revisit:** a second deployable is needed (mobile BFF, long-running worker).
- **Evidence:** prompt §6; Next 16 docs (Node runtime, Turbopack).

### D2 — pnpm
- **Decision:** pnpm 11, no workspaces.
- **Options:** npm; yarn; pnpm.
- **Choice:** pnpm (installed, fast, strict peer resolution exposes AI SDK/Zod mismatches early).
- **Revisit:** never in this phase. **Evidence:** `01 §10`.

### D3 — Supabase Postgres, SQL migrations, supabase-js with generated types, no ORM
- **Context:** RLS is the security backbone; every query must run as the user.
- **Options:** (a) Drizzle/Prisma with a pooled connection (bypasses RLS unless `set role` per request); (b) PostgREST via supabase-js with generated types; (c) raw `pg` with manual role switching.
- **Choice:** (b) plus `security definer` SQL functions for multi-table transactions. Trade-off: SQL functions are tested only by DB-integration tests; accepted.
- **Revisit:** more than three defects traced to hand-written SQL composition.
- **Evidence:** Supabase local-development and migration docs (§2).

### D4 — Single database, `institution_id` everywhere, RLS via `security definer` helpers on `memberships`
- **Options:** (a) custom JWT claims via the access-token hook; (b) schema-per-tenant; (c) helper functions reading `memberships`.
- **Choice:** (c), helpers in non-exposed `app` schema with `set search_path = ''` and `(select auth.uid())`. Trade-off: one indexed lookup per policy evaluation; claims would be faster but refresh only on token reissue and complicate multi-institution users.
- **Revisit:** policy evaluation > 5 ms p95 at demo scale (measure) → consider claims for role only.
- **Evidence:** Supabase RLS and custom-claims guidance (§2).

### D5 — Path-based tenant routing, public site at `/s/[slug]`
- **Options:** subdomain per institution now; path-based now with subdomain rewrite later.
- **Choice:** path-based; `proxy.ts` can rewrite subdomains later without touching pages.
- **Revisit:** custom domains (F-WEB-05). **Evidence:** D24 (proxy is Node-only and supports rewrites).

### D6 — Two-layer authorization with a static TypeScript permission matrix
- **Options:** (a) RLS only; (b) application checks only; (c) both, matrix in code; (d) both, matrix in a table.
- **Choice:** (c). RLS uses coarse role sets mirroring the matrix's read columns; a generated suite asserts consistency (C-01, C-03). Trade-off: role changes need a deploy.
- **Revisit:** F-IDN-05. **Evidence:** `07 §2`, `05 §5`.

### D7 — Server Actions for authenticated mutations; Route Handlers for public/AI/cron; uniform envelope
- **Context:** Next 16 Server Functions bypass proxy matchers; every action re-verifies.
- **Options:** REST route handlers for everything; tRPC; Server Actions.
- **Choice:** Server Actions + `defineAction` wrapper (validation, permission, envelope, registry). Trade-off: harder to call from non-browser clients; acceptable for the demo.
- **Revisit:** mobile app or partner API. **Evidence:** Next 16 proxy docs (§2).

### D8 — Service-role allow-list
- **Decision:** service role only in seed/reset, the job runner, and named `security definer` functions (`07 §4`); admin client guarded by `SERVICE_ROLE_CALLER` and an ESLint import restriction.
- **Options:** free use of service role in actions (fast, unsafe); allow-list.

### D9 — AI via Vercel AI SDK v7 behind one gateway
- **Context:** no cloud key; a 6 GB GPU; policies must be enforceable and testable.
- **Options:** (a) direct Anthropic SDK + direct Ollama HTTP; (b) AI SDK with providers; (c) LangChain.
- **Choice:** (b): `generateText` + `Output.object` for Zod output; `createUIMessageStreamResponse` for streaming; local provider `ai-sdk-ollama@^4.6` (peer `ai@^7`, structured outputs documented), alternative `ollama-ai-provider-v2@^4`; cloud `@ai-sdk/anthropic@^4`. ### D27 — App-layer audit events go through `public.record_audit_event`
- **Context:** `04 §D20` has actions call `audit(ctx, …)`, and T-015/T-027 import `src/lib/audit.ts`, but no packet created it, and `app.audit()` is in the unexposed `app` schema.

### D28 — Teacher tool-calling agent runs on Gemini (cloud), student data included
- **Context:** owner asked (2026-10-30) for a real multi-turn, tool-calling AI agent (not the existing one-shot `runStructured` drafts), starting with the teacher role. L2-02's documented rule is that features touching student data (names, marks, attendance) stay local-only or on a paid tier excluding training on customer data; free-tier cloud is curriculum-only.
- **Verified before choosing:** the configured local model (`qwen2.5:3b` — the only model actually pulled; `.env.local`'s `qwen3:4b-instruct` default is not present locally) completes a real tool-call round-trip correctly in ~3.7s via the standard `ai` v7 `generateText({tools, stopWhen})` loop against `ai-sdk-ollama`. Gemini's flagship free-tier model (`gemini-3.8-flash`) also completes correctly but took ~400s per call twice in a row (not a retry artifact — reproduced with `maxRetries: 1`), unusable for a live chat; the **lite** tier (`gemini-flash-lite-latest`) completes correctly in ~5s, comparable to local.
- **Decision:** the teacher agent (and only the teacher agent, for now) uses `gemini-flash-lite-latest` for every tool, including the student-lookup/attendance/remark tools that touch student data — **owner-approved exception** to L2-02's locality rule, made explicitly after the latency finding above, not a silent default.
- **Still holds:** rule 6 (AI drafts, a human reviews and saves; the agent never writes marks/payments/access/welfare itself) and every tool's execution still runs through the teacher's own authenticated session (RLS/permission-scoped), never an admin/service-role client — the model only chooses which already-scoped function to call and with what arguments, it is not a new trust boundary.
- **Not resolved:** other roles' agents, if/when built, each need their own data-class call — this ADR is scoped to the teacher agent only, not a blanket "Gemini is fine for student data" ruling.
- **Revisit:** if `gemini-flash-lite-latest` is deprecated/retired the way `gemini-2.5-flash` was mid-session, or before extending cloud-for-student-data to any other role's agent.

### D29 — Teacher agent routes between Groq (routine) and Gemini (complex)
- **Context:** owner asked whether a small/cheap model could run alongside Gemini, routing "difficult" queries to Gemini and "routine" ones to the cheap model, to reduce load on Gemini. Owner supplied a Groq API key (`gsk_...`) directly, so Groq was added as a second cloud provider (same shape as D28's Gemini addition) rather than Vercel's own AI Gateway — simpler, verified faster, matches the key in hand.
- **Verified before choosing:** key confirmed valid via `GET /v1/models` before any build; no `llama-3.x` models on this key, only `openai/gpt-oss-20b`/`-120b` and `qwen/qwen3.8-27b`. Both gpt-oss sizes completed a real tool-call round-trip correctly; `-120b` was both faster (970ms vs 1766ms) and no worse in output quality on this test than `-20b` — so `-120b` is the default, no separate "cheap tier" env knob.
- **Honest limit, stated before building:** the teacher agent's top-level model only picks a tool and summarizes the result in 1–3 sentences — the one genuinely hard generation task (drafting a full quiz or report-card remark) already runs through a *separate* `runStructured` call inside the tool itself (`teacher-tools.ts`), not this model. So there is no strong intrinsic difficulty split to route on at this layer; this routing is a cheap, explainable v1, not a rigorous classifier, and the owner was told so before it was built.
- **Decision:** `pickAgentProvider` (`src/modules/ai/agent/provider-routing.ts`) routes by message length (>220 chars → gemini) and a short multi-part-cue regex ("and also", "as well as", "compare", "both" → gemini); everything else → groq. Each provider gets its own concurrency bucket (`${institution}:${provider}`) and fails closed independently if its own key is unset (same `ai_unavailable` contract as D28, never a silent fallback to the other provider).
- **Still holds:** rule 6 and D28's "every tool runs through the teacher's own RLS-scoped session" — routing only changes which model drafts the reply/picks the tool, never which data a tool can reach.
- **Revisit:** if a genuinely hard-vs-easy signal shows up at this layer (unlikely given the current tool set), or if Groq retires `openai/gpt-oss-120b` the way Google retired `gemini-2.5-flash` mid-build.

### D30 — Per-institution feature entitlements (v1 slice)

- **Context:** owner wants control over which features each customer (institution) gets, separate from the existing role→permission matrix (F-IDN-04/05), which only governs *who inside* an institution can use a feature already available to it. No entitlements concept existed before this.
- **Decision:** reuse `institutions.settings` (existing jsonb column, no migration) with a new `features: Record<string, boolean>` key, validated by the same `InstitutionSettingsSchema` (`src/modules/core/schemas.ts`) that already owns this column's shape. `isFeatureEnabled(ctx, key)` (`src/lib/auth/entitlements.ts`) reads it: a key that is explicitly `false` disables the feature; a missing key, a missing `features` map, or settings that don't parse as an object all default to **enabled**. This means adding a new gated feature here can never silently take an existing feature away from an institution whose `settings` predate the key — the opposite failure mode (forgetting to enable a feature for an existing customer) was judged the safer default to bias toward for a v1 with no admin UI yet.
- **First real gate:** the teacher AI agent route (D28/D29) checks `isFeatureEnabled(ctx, "teacher_ai_agent")` right after its role check and before quota/concurrency work, failing the same way an unconfigured provider key already does (`ai_unavailable`, reusing the existing `ErrorCode` rather than adding a new one) — "not on this institution's plan" and "not configured" are both forms of the same honesty contract (rule 7: no silent fallback).
- **Scope deliberately cut here (not built yet):** no admin UI or action to *toggle* a flag — today it's only settable by hand-editing `institutions.settings` (seed, SQL, or a future admin action). No per-feature catalog/enum of known keys — `features` is `Record<string, boolean>` on free-form string keys, matching `numbering`'s existing pattern in the same schema, not a closed union. Only one feature (`teacher_ai_agent`) is wired to a real gate; the rest of the feature matrix (03) is unaffected until each is deliberately gated the same way.
- **Still holds:** rule 2 (RLS + `requirePermission`) is untouched — entitlements are a third, orthogonal gate (*does the institution's plan include this at all*), checked in addition to, never instead of, permission/role checks.
- **Revisit:** when a second feature needs gating, or when the owner wants a platform-admin UI to flip flags instead of editing `settings` directly — at that point, consider whether `features` should become a closed key enum (catches typos) and whether toggling needs its own permission (likely `isPlatformAdmin`-only, not `institution.settings.manage`, since this is the platform controlling what it gives the customer, not the customer configuring itself).
  - **Superseded in part by D33** (2026-10-30): the second feature arrived (the generative-UI plan, `14-generative-ui-plan.md`), and the closed-key-enum half of this revisit note was taken. The toggle-authority half was explicitly NOT taken — see D33.

### D31 — Generative UI: closed 7-block Zod catalog, no framework

- **Context:** `14-generative-ui-plan.md` §3–4 recommends against every third-party generative-UI framework surveyed (CopilotKit, Tambo, Thesys, json-render, A2UI, `@ai-sdk/rsc` `streamUI`) on cost, vendor-lock-in, or maturity grounds, in favor of building a small closed catalog on the AI SDK v7 tool-parts pattern this codebase's teacher agent already uses.
- **Decision:** `src/modules/ai/blocks/schemas.ts` defines 7 block `kind`s as a `z.discriminatedUnion("kind", [...])`: `notes`, `table`, `flashcards`, `practice`, `callout` (GU-03), `mindmap`, `chart` (GU-04). Every field is a capped, plain string/number/enum — never markdown or HTML — so `BlockRenderer.tsx` (one dispatch point, one component per kind) never needs `dangerouslySetInnerHTML`. String caps stay well under DBT-27's measured ~2000-char Ollama grammar-compiler crash boundary (the catalog must work for the local model, not only cloud ones). Lists are flat, never recursive — `mindmap`'s `parentId` is a flat adjacency reference, not nesting (recursive schemas are fragile across Gemini/Groq/Ollama structured output). `practice` reuses `quiz.schemas.ts`'s `QuizGenerationQuestionSchema` (now exported) rather than re-specifying the same shape, plus its own `superRefine` for option-uniqueness/answer-validity that schema deliberately omits (that schema's own documented contract: the quiz route re-validates after generation; this catalog has no such second pass, so the check had to live here — found in `react-reviewer`'s review of this packet, fixed before this commit). `mindmap` depth (≤4) and cycles are rejected by `superRefine`; a node whose `parentId` doesn't resolve to another node in the block is tolerated by the schema and dropped instead by `mindmap-layout.ts`'s pure `buildTree` (a model's one bad reference shouldn't lose an otherwise-good mindmap). `chart` has no `dataRef` binding yet — literal numbers only; `dataRef` (binding a chart/table to a tool's real output, so teacher-facing charts can say "From school records" instead of "AI-generated numbers") is GU-17, wave 2, deliberately not built here.
- **Still holds:** rule 6 — nothing in this catalog saves anything; `practice` is explicitly never written to `assignments` (scratch-only, same boundary as the teacher agent's existing draft tools).
- **Review:** `react-reviewer` found 3 HIGH (practice answer-validity gap above; callout tone was color-only, now also icon-coded; practice's option list was keyed/compared by text, now by index) and 3 MEDIUM (unnecessary `"use client"` on the dispatcher, removed; notes heading level unverified against a real page, downgraded from `<h3>` to plain emphasis text; flashcard flip button missing `aria-pressed`, added) — all fixed before this commit.
- **Revisit:** per `14-generative-ui-plan.md` §10 — the catalog grows past ~12 kinds, or nested/composed layouts are needed (re-evaluate json-render if it reaches 1.0, or A2UI); once `NotesBlockView` is actually wired into a page (GU-08), confirm its heading level against the real hierarchy instead of leaving it downgraded indefinitely.

### D32 — Student AI: local-only v1, student-only chat visibility, no cloud yet

- **Context:** `14-generative-ui-plan.md` (GU-05/GU-07/GU-08) proposed a student study-chat feature. Its own cost research found free-tier Gemini/Groq unsuitable for minors' data (Gemini's free tier: "content used to improve our products"; Groq's free 200K tokens/day would starve a whole school), meaning any cloud path requires a real paid-tier key — a billing decision the owner had not made. Separately, the plan's own default (guardian/teacher visibility of student chats) and the default retention/deletion rule needed an explicit owner answer, not an assumed one, given DPDP exposure (minors' personal data).
- **Decision:**
  1. **Local-only v1.** `ai_policy` must be `local_only` for any institution to use `student_ai_study`; `cloud_allowed`/`local_with_cloud_fallback` institutions get `ai_policy_blocked` until a future paid-tier decision is made (no free-tier cloud path for student data, ever — matches rule 6/D28's existing cloud-disclosure discipline, just stricter, since L2-02's "not usable for minors' free text on a free tier" finding is now binding, not advisory).
  2. **Student-only, ever.** No role — not guardian, not teacher, not owner/principal/admin — can read a student's saved chats or notes through the app. RLS is own-rows-only for `study_items`/`study_preferences` (GU-07), no exception.
  3. **Retention:** the student may hard-delete their own content at any time; `demo:reset` clears all of it for the demo tenant, same as every other demo-reset guarantee.
  4. **Data class:** `Confidential` (`07 §3`'s own four-value scale — Public/Internal/Confidential/Restricted; there is no separate "minors' data" or "restricted" tier in that doc, so this does not invent one).
- **Still holds:** rule 6 (AI output is a human-saved suggestion; a student's own saved note is the student's own save, same boundary as a teacher's).
- **Revisit:** before any real (non-demo) school uses this — get the DPDP legal review the generative-UI plan flagged (§9), then revisit whether a paid-tier cloud path is worth adding, and set the per-student daily token cap from measured usage rather than the placeholder in GU-05.
- **GU-05 implementation (2026-10-31):** this decision landed as `streamAgent` in `src/lib/ai/gateway.ts`, a streaming sibling to the existing `runStructured` (same permission/quota/concurrency/usage-logging gates; a stream, once started, has no fallback-to-a-second-provider, unlike `runStructured`'s retry ladder — there is no point left to fall back from once bytes are already reaching the client). Point 1 above simplified the packet considerably from the plan's own text: no `AI_CLOUD_PAID_TIER` env attestation was built, because there is no cloud path to attest to yet at all (see below) — that plumbing is deferred until a real paid-tier decision makes it necessary.
  - `security-reviewer` (Opus) found 2 HIGH before this landed, both fixed: (1) the `dataClass` gate was optional and failed open on an omitted/mistyped value — now required, fails closed on anything other than the literal `"general"` opt-out; (2) the cloud step sent the full multi-turn transcript (tool results included) with no redaction, reachable by any future general-purpose caller whose plan ever included cloud — rather than build real `prepareStep`-based redaction for a cloud caller that doesn't exist yet, the cloud step is refused unconditionally inside `streamAgent` until one does.
  - Also fixed from that review (MEDIUM/LOW): `abortSignal` is now required, not optional (a disconnected client must not keep holding a shared concurrency slot); a per-step `timeout` was added, matching `runStructured`'s own `TIMEOUT_MS`; `maxOutputTokens` defaults to 2048 instead of being unbounded; an explicit `onError` logs a correlation id instead of the SDK's default raw-error console dump; the `redactions` count is now wired to the real redaction result instead of a hardcoded `0`.

### D33 — Feature catalog v2: closed key set, per-key defaults, toggle authority unchanged

- **Context:** `14-generative-ui-plan.md` §7 proposed two changes to D30 ahead of building eight new feature keys for the generative-UI work: (1) a closed, typed key set instead of D30's open `Record<string, boolean>`, each with its own default instead of D30's blanket "missing key = enabled"; (2) moving toggle authority from the institution (`institution.settings.manage`) to the platform (`is_platform_admin` only), arguing "ask 2" ("we control which customer gets what") meant *the platform* decides, not the school.

### D34 — `defineAction`'s test-only `overrideCtx` was a real, codebase-wide auth bypass

- **Context:** `src/lib/actions/define-action.ts` (T-008) has accepted a third argument, `overrideCtx`, since the very first packet — documented as "test-only: bypasses context resolution entirely (`tests/helpers/actions.ts` `callAs`)". GU-09's security review (Opus, 2026-10-31) found that this comment described the *intended* use, not the only *possible* one: every `"use server"` file compiles each export into a real HTTP endpoint, and Next.js's own action handler decodes whatever argument array a request carries and calls the function with it (`action.apply(null, args)`) — there is no framework-level enforcement that a caller supplies only the two arguments a legitimate client-side call site would ever send. A signed-in attacker who discovers an action's id (derivable from the client bundle, since the action must be referenced there to be callable at all) could, in principle, send a crafted third argument shaped like a `TenantContext` — skipping `getTenantContext` and `hasPermission` entirely, for **every** `defineAction`-based action in the app, not only the four GU-09 added. RLS was always the real backstop regardless (every exploit scenario the review traced still ended at RLS correctly blocking cross-tenant/cross-user access), but rule 2's *first* layer — "`requirePermission` in every action" — was silently a no-op against this specific attack shape, across the whole codebase, since T-008.
- **Decision:** `overrideCtx` is now honored only when `process.env.VITEST === "true"` (set by Vitest itself at process start, never by a request body/header/argument — a build-time/process-level fact, not something any caller can influence) — any other value returns `forbidden` before `ctx` is ever assigned. This required **zero changes to any existing test file**: every test across the suite reaches this code already running under Vitest, so `callAs`/`buildContext`'s existing pattern keeps working unchanged. Verified: the entire `pnpm test:db` (350/350) and `pnpm test:security` (1098/1098) suites pass unmodified after the fix, plus two new unit tests in `tests/unit/define-action.test.ts` proving the gate rejects a forged `overrideCtx` with `process.env.VITEST` unset and still accepts it when set.
- **Why this fix and not a `NODE_ENV` check (the review's own first suggestion):** `NODE_ENV !== "production"` would still leave the bypass open on a `next dev` server (dev builds are commonly left reachable during local demos on this project, per this session's own earlier work finding a full local Supabase stack running unnoticed) — `VITEST` is true only inside an actual Vitest process, in every environment, including dev.
- **Still holds:** rule 2's two-layer model is now actually two layers again, not one (RLS) with a decorative one (the permission check) — this was true of every write action in the app, including finance, exams, admissions, and attendance, not something specific to AI features.
- **Revisit:** the review flagged that it did not audit which other actions have RLS *weaker* than their own app-level permission check — those are the ones this exact bypass would have actually mattered for in practice (actions where RLS alone permits something the permission check was meant to additionally restrict). That audit has not been done. Until it is, treat "RLS was the real backstop" as true for every case the review happened to trace, not as a verified property of the whole action surface.

### D35 — GU-09 notebook: per-item cap enforced at the DB level; ownership checks on an optional link; URL-param hardening

- **Context:** GU-09 (the student notebook — save/organize/reopen chats and notes) landed with its own security review (Opus, 2026-10-31), which found D34 above (the dominant finding) plus notebook-specific issues.
- **Decision:**
  1. **Per-student item cap moved into the database.** `student-study.actions.ts`'s own 200-item check ran in the app only; any signed-in member could insert directly through the Data API (their own real session, RLS-permitted — 0049's insert policy has no count limit) and skip it entirely, and each row allows up to ~256 KB, so unbounded inserts could fill a shared database. `20261028000050_study_items_cap.sql` adds `app.guard_study_item_cap()`, a `BEFORE INSERT` trigger taking a per-user advisory lock (closes the count-then-insert race too) and rejecting the 201st row with `code:validation_failed`. The app-level check stays, only for the friendly message before a round trip finds out the same thing.
  2. **`sourceChatId` ownership/kind-checked, not just schema-shaped.** A client could set a note's `sourceChatId` to any UUID — FK checks ignore RLS, so without a check it could point at another student's or another school's chat, or at a note instead of a chat. `saveStudyNote` now resolves it through the caller's own RLS client first (`.eq("kind", "chat")`) and silently drops it if nothing comes back, rather than linking it or surfacing an error (no existence oracle on this optional field).
  3. **Explicit `institution_id`/`user_id` filters added to `updateStudyItem`/`deleteStudyItem`'s own queries** — defense in depth matching `student-study.queries.ts`'s existing pattern; RLS already enforced this, the filters just mean the query itself doesn't rely on that twice.
  4. **`getStudyItem`'s chat branch now re-validates `messages`** the same way the note branch already re-validated `blocks` (via the shared `UIMessageRequestSchema`) — a row written through the Data API with a malformed shape would otherwise crash rendering the student's own `?resume=` page. Both branches now guard `content` being `null`.
  5. **URL-derived values are validated before use, not just typed.** `resume` and `[itemId]` are checked against `uuid` before reaching Postgres (a non-UUID string previously surfaced as a raw 500, `22P02`, instead of "not found" or a fresh chat); the notebook list's `folder`/`search` are guarded against Next's real runtime possibility of `string[]` for a repeated query param (a narrower type annotation doesn't prevent this at runtime).
- **Checked and confirmed clean by the review, not changed:** resuming a saved chat does **not** reintroduce GU-08's own fixed history-forgery risk — the live route's `stripToUserText` runs on every request regardless of where the history originated, and no server code path sends a stored `study_items` row to a model directly. Note-block re-validation on read was already real (not cosmetic). Audit calls already carried no title/content. Cross-user update/delete already correctly resolved to `not_found` via RLS.
- **Still holds:** D32 (own-rows-only, no staff exception) — nothing here changes who can see what, only how robustly identity/links/inputs are checked before reaching the data.
- **Revisit:** the review's test-gap list (no action-level delete-by-another-user test, `sourceChatId`/queries.ts coverage) was closed in the same commit as this ADR; nothing deferred from GU-09's own review remains open.

### D36 — Live bug-hunt sweep across all 9 roles (2026-10-31): two real bugs fixed, four reported findings refuted after independent verification

- **Context:** after GU-09 shipped, the owner asked for the running app to actually be tested — not reviewed — live, against the real seeded demo tenant, across every role, plus a full feature inventory.   1. **`runGenerateTermInvoices` (`src/modules/finance/actions.ts`) failed on any grade with more than ~150 active students** with a generic "Something went wrong" — the existing-invoice check built a single `.in("student_id", studentIds)` request with every student id in the URL query string; for a real-size grade (Grade V in the demo tenant: 252 students) this produced a URL long enough to hit the server's own URI-length limit ("URI too long", confirmed in the dev server's own log via the error's correlation id). Two genuinely new bugs survived that bar; four did not.
