## Findings

`supabase/migrations/20261028000079_invitation_rpcs.sql:1516-1559` (revoke_invitation): MEDIUM: TOCTOU — the function reads the invitation row with a plain `select` (no `for update`), checks `accepted_at`/`revoked_at`/`expires_at`, then does a separate `update ... set revoked_at = now() where id = p_invitation_id` with no re-check in the `where` clause. A concurrent `accept_invitation` (which does take `select ... for update`) can insert the membership and set `accepted_at` between revoke's read and its write; revoke's `update` then still succeeds, leaving the row both accepted and revoked with no error returned to the admin — the admin is told the revoke worked while the membership was actually created. Fix: make the final write self-checking and atomic, e.g. `update public.invitations set revoked_at = now() where id = p_invitation_id and accepted_at is null and revoked_at is null and expires_at > now() returning id into v_id; if v_id is null then raise exception 'code:invalid_state' ...;` (or take `select ... for update` first, same pattern already used in `accept_invitation`).

`supabase/migrations/20261028000064_onboarding.sql:1109-1114` (create_institution): MEDIUM: quota check is not atomic — `select count(*) ... where user_id = v_uid and role = 'owner' and status = 'active'` is read, compared `>= 3`, then a new institution + owner membership is inserted, with no lock between the count and the insert. Two (or more) concurrent `create_institution` calls from the same signed-in user can all read the pre-insert count and all pass the `< 3` check before any of them commits, letting one user exceed the per-owner cap of 3 institutions. Fix: `perform pg_advisory_xact_lock(hashtext(v_uid::text));` before the count, so concurrent calls from the same user serialize on the check.

`supabase/migrations/20261028000064_onboarding.sql` (create_institution) and `supabase/migrations/20261028000079_invitation_rpcs.sql` (invite_member): LOW: NULL-arguments bypass the hand-written validation `if` branches instead of hitting `code:validation_failed`. Postgres NULL-propagation means `length(null) < 2`, `null !~ pattern`, `null = any(array[...])`, and `p_role not in (...)` all evaluate to NULL, which `if` treats as false, so a direct `supabase.rpc('create_institution', {p_name: null, ...})` / `rpc('invite_member', {p_role: null, ...})` call (bypassing the Zod schema in the Next.js route, which is the only thing currently stopping this) falls straight through every explicit check and only fails later on a bare NOT NULL/CHECK constraint violation. Not exploitable for a bypass (the insert still fails and `mapSqlError` returns a generic `internal` with no raw SQL leaked), but it defeats "validate at every trust boundary" for a function reachable directly over PostgREST. Fix: add `if p_name is null or p_slug is null then raise exception 'code:validation_failed' ...; end if;` (and `p_role is null` in `invite_member`) ahead of the existing checks.

`src/modules/academics/setup.actions.ts:194-198`: LOW (doc/comment accuracy, not a live vulnerability): the comment claims "subject_assignments' own RLS (0005) was not extended by 0065 ... plain FKs here are not yet bound to the caller's institution at the RLS layer" — this is incorrect. `supabase/migrations/20261028000036_enrolment_subject_assignment_fks.sql` already bound `class_section_id`/`subject_id`/`teacher_id` to `institution_id` on `subject_assignments` INSERT/UPDATE (confirmed by reading that migration). The app-layer `assertInInstitution` check this comment justifies is therefore redundant-but-harmless (no vulnerability), but the wrong comment could mislead a future change into treating the app-layer check as the sole defense, or into skipping a real audit of an actually-unpatched table elsewhere. Fix: correct the comment to cite 0036.

## Checked, no issue found

- Escalation gating: `app.guard_membership_write` (0064's `create or replace`) is additive-only over 0033 — service_role/postgres bypass, then the new bootstrap-bypass GUC, then (new) user_id/institution_id immutability, then self-edit block, then owner/principal escalation checks, all preserved; diffed line-by-line against 0033, no weakening. `invite_member`/`revoke_invitation` mirror the same owner/principal escalation rule and apply it independently at the RPC layer (defense in depth with the trigger).
- Bootstrap GUC (`app.allow_membership_bootstrap`) is only ever `set_config`'d inside `create_institution`/`accept_invitation`'s own definer bodies; `app` schema has no PostgREST exposure and PostgREST does not let a client set arbitrary custom GUCs, so it is not reachable from outside the two definers. `accept_invitation` resets it to `''` immediately after its own membership insert (not left to transaction end); `create_institution` performs no further membership write after setting it, so the open window is inert.
- `setMemberRole`/`setMemberStatus` (`src/modules/core/actions.ts`): both scope the update with `.eq("institution_id", ctx.institution.id)`, use `.maybeSingle()` with an explicit `not_found` (no PGRST116-swallowed cross-tenant probe). `app.validate_membership_link` (0002) fires on every UPDATE too, so `setMemberRole` can only move a membership between roles that already share the same link-column shape (confirmed: a student/guardian membership cannot be silently turned into a staff role, since `staff_id` stays null and the trigger rejects it). Self-escalation and non-owner edits of owner/principal memberships are blocked by `app.guard_membership_write`, independent of the action layer's own `member.manage` permission check (two-layer defense).
- `updateInstitutionSettings`: the DB update object only ever contains `name`/`settings`; `slug`/`is_demo` columns and any `ai_policy`-style key are never in the allow-listed update, and `InstitutionSettingsSchema` (the only shape `settings` validates against) has no `ai_policy`/`is_demo` key, so there is no way to smuggle either through this action.
- Cross-tenant FK binding on every new/touched user-writable table: `grades`/`subjects`/`departments` have no cross-table FK to bind; `class_sections` (grade_id, academic_year_id, class_teacher_id) and `staff` (department_id) and `terms` (academic_year_id) are bound by this diff's own 20261028000065; `subject_assignments` (class_section_id, subject_id, teacher_id) was already bound by the pre-existing 0036 (plus a redundant app-layer check, see LOW finding above). Role sets on the rewritten policies (0065) are unchanged from the originals (0002/0004/0005) — confirmed by diff, only the FK `exists`/`staff_in_institution` clauses were added.
- Reserved-slug list in `create_institution` (`api, s, login, logout, auth, admin, app, www, static, public, demo, invite, onboarding`) covers every actual static top-level route under `src/app` (`api`, `s`, and the `(auth)` group's `login`/`logout`); `(tenant)/[institution]` is the intended dynamic catch-all, not a conflict.
- Token: `invite_member` generates 32 random bytes (`extensions.gen_random_bytes`) → 256-bit token, returned once; only its sha256 hex is persisted in `token_hash`, which has no SELECT grant to `authenticated` (0064's explicit column grant list omits it) — not recoverable even by an admin query. `accept_invitation` hashes the caller-supplied token the same way, takes `select ... for update` on the matching row (closing the concurrent-double-accept race the migration's own comment calls out as "fix round 1"), and the `unique_violation` exception handler plus the `accepted_at`/`revoked_at`/`expires_at` state checks make acceptance single-use.
- Email-match / link-reuse on accept: caller's `auth.users.email` (lower-cased) must equal the invitation's already-lower-cased `email`; a linked `staff`/`guardians`/`students` row already owned by a different `user_id` is rejected before the membership insert (the diff's own "fix round 1" note), preventing one invitation link from being hijacked onto an unrelated account.
- No PII in audit rows: `core.member.invite` audits `{role}` only (comment explicitly calls out omitting email); `people.staff.upsert` audits designation/isTeaching/status only, no phone/email; the SQL-side `invite_member`/`accept_invitation`/`revoke_invitation` audit calls carry only `{role}`; `audit()` (`src/lib/audit.ts`) never auto-includes anything beyond what a caller explicitly passes.
- CSRF/cookie handling on the two new non-tenant routes: both go through `readPostBody` → `isCrossSiteRequest` (origin/`sec-fetch-site` check) before touching the body, both call `getClaims()` (re-validates the JWT, never trusts the raw session cookie), and both correctly support either the cookie session or an `Authorization: Bearer` token via `withBearerToken`/`AsyncLocalStorage` scoping (request-local, confirmed it does not leak across requests).
- `mapSqlError`: every new `raise exception 'code:...'` detail string reviewed is free of PII/raw SQL (e.g. "invitation was issued to a different email address" — no email value inlined); anything not matching `code:<known>` is logged server-side with a correlation id and returned to the client as a generic `internal`, never raw Postgres text.
