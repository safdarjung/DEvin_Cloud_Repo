# M10 security review (Sonnet security-reviewer, captured by controller from workflow result)

- **MEDIUM** `src/modules/academics/curriculum.actions.ts` — upsertLessonPlan's update path (id given) runs the unit/grade pre-check via loadSectionGrade(ctx.institution.id, classSectionId) using the CLIENT-SUPPLIED classSectionId, not the lesson plan row's real persisted class_section_id (which the update never touches). A caller can pass a classSectionId that doesn't match the row actually being updated, so the app-level validation_failed/curriculumUnitId pre-check is evaluated against the wrong section's grade. RLS's WITH CHECK still re-validates against the real stored class_section_id (table-qualified `lesson_plans.class_section_id`), so this is NOT an authorization bypass -- but it produces wrong error codes/messages (e.g. a real mismatch slips past the app pre-check and surfaces as a generic 42501 'forbidden' instead of validation_failed, or a valid update is wrongly rejected as validation_failed). Fix: for the update branch, fetch the existing row's class_section_id (and subject_id) from the DB by id+institution_id first, and run the pre-check against that, not the client-supplied value.
- **MEDIUM** `tests/db/curriculum-actions.test.ts` — No test exercises the update (`id` provided) branch of curriculum.lessonPlan.upsert at all -- every TEST FIRST case in M10-T3 and every test in this file only inserts (no `id`). The update path (which freezes class_section_id/created_by via the guard trigger but still re-runs the unit/grade pre-check against client input, per the finding above) is completely unverified. Add a test that updates an existing lesson plan's title/objectives/curriculum_unit_id and one that attempts to move/escalate via a mismatched classSectionId on update.
- **LOW** `supabase/migrations/20261028000072_curriculum_coverage.sql` — No explicit `grant ... on table` statements for lesson_plans/curriculum_unit_coverage in this migration (unlike some older migrations). This is NOT a gap: migration 20261028000045_explicit_api_grants.sql installed `alter default privileges for role postgres in schema public grant all on tables to anon, authenticated, service_role`, which auto-grants these privileges to any new table created by the postgres role (same pattern 0069/timetable relied on) -- RLS remains the real access control. Noting only for the reviewer's confirmation trail, no fix needed.
- **LOW** `src/modules/academics/curriculum.schemas.ts` — LessonPlanUpsertSchema.resources and CurriculumUnitUpsertSchema.description are `.optional()` but not `.nullable()`, so a caller can never clear an already-set resources/description value back to null via upsert (omitting the key leaves the column untouched only on update since the action spreads `...(resources !== undefined ? {resources} : {})` -- there's no way to explicitly set it to null). Minor UX/correctness gap, not a security issue; flag for product follow-up only if clearing is a required feature.
