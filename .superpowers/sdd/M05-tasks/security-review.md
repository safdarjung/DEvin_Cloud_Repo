# M05 documents/storage — security review

Scope: migration `supabase/migrations/20261028000067_documents.sql`; `src/modules/documents/{schemas,actions,queries,query-defs}.ts`; permissions `document.read`/`document.write` in `src/lib/auth/permissions.ts`. Diff read: `.superpowers/sdd/M05-tasks/m05-diff.patch`. Rulings read: `docs/planning/fabric/06-backend-packets/M05-tasks.md` header; `.superpowers/sdd/10-backlog-index/BRIEF-COMMON.md` lessons.

## Findings

supabase/migrations/20261028000067_documents.sql:60-97,153-168: MEDIUM: `app.guard_documents_update` only constrains the `status` column's transitions (pending→active, active→deleted) and the identity columns (institution_id/entity_type/entity_id/path/created_by/mime). It does not constrain `deleted_at`/`deleted_by`, and does not require `deleted_by = app.current_user_id()` the way insert requires `created_by = app.current_user_id()`. Any caller who already satisfies `documents_update` RLS (owner/principal/admin, or admissions on a student/application row) can, by calling PostgREST directly: (a) set `deleted_by` to an arbitrary other profile id, misattributing who deleted a document; (b) set `deleted_at`/`deleted_by` on a row while leaving `status` unchanged (e.g. still `'active'`), producing an inconsistent half-deleted state; (c) re-issue a `'deleted'→'deleted'` update to silently overwrite `deleted_at`/`deleted_by` on an already-deleted row, since the trigger's transition check only fires `when new.status is distinct from old.status`. None of this grants unauthorized *read* access (storage still requires `status='active'`), so it is an audit-integrity gap, not a confidentiality/authorization bypass. Fix: extend the guard trigger to (1) require `new.deleted_by is null or new.deleted_by = app.current_user_id()` whenever `deleted_by` changes (service_role/postgres bypass excepted, as already done for other fields), (2) require `deleted_at`/`deleted_by` to be set together with, and only with, the `active→deleted` transition, and reject changing them in any other update (including `deleted→deleted` no-ops).

supabase/migrations/20261028000067_documents.sql:124-151 (`documents_insert`, `entity_type = 'submission'` branch): LOW: unlike `student`/`staff`/`application`, there is no `exists(...)` check binding a `submission` row's `entity_id` to anything, because the backing table doesn't exist yet (M9). This is explicitly called out and accepted in the migration's own header comment ("acceptable because only owner/principal/admin can insert that type at all, and institution_id itself is still role-gated") and the app layer additionally blocks it today (`requireVisibleEntity` throws `validation_failed` for `submission`). Only reachable by bypassing the Next action and calling PostgREST directly as owner/principal/admin, and `documents_select` has no reader for `submission` yet either, so there is no read-side impact today. Flagging only so the M9 packet that adds the `submission`-backed table also adds the same cross-table/institution check used for the other three entity types, before any reader is wired up.

src/modules/documents/schemas.ts:16 (`fileName`) / src/modules/documents/actions.ts:172 (`getReadUrl` returns `fileName: doc.file_name`) / src/modules/documents/queries.ts (`listDocumentsForEntity` returns `fileName`): LOW: `file_name` is free-form user input (1–200 chars, no character allowlist) stored verbatim and returned to callers. Nothing in this diff renders it unsafely (no UI code here, and it is correctly kept out of `audit()` metadata — only ids are logged, per the `document.upload_requested`/`document.read_url`/`document.delete` calls in actions.ts), so this is not an active XSS/injection in the reviewed code. Flag for whichever UI consumes `getReadUrl`/`documents.listForEntity`: render `fileName` as text (React's default escaping, no `dangerouslySetInnerHTML`) and don't use it unescaped in a `Content-Disposition` header or shell/log context.

src/modules/documents/actions.ts (`requestUpload`, `getReadUrl`): LOW / informational: no rate limiting on signed-upload-URL or signed-read-URL issuance beyond the permission check, so a `document.write`/`document.read` holder could flood pending rows or burn signed URLs. This matches the rest of the reviewed codebase (no module-level rate limiting seen elsewhere either), so it's a pre-existing platform gap, not a regression introduced by M05 — noting per the common security checklist's "rate limiting on all endpoints" item rather than blocking this packet on it.

## What I checked (no CRITICAL/HIGH found)

- Cross-tenant/cross-entity read via direct Storage API (`list`, `download`, `createSignedUrl` on guessed paths, `search` prefix tricks): blocked — `tenant_docs_select`'s `exists` subquery against `public.documents` is a plain (non-definer) select, so it is itself re-filtered by `documents_select` RLS; confirmed in `tests/db/documents-acceptance.test.ts` (`directDownloadB` from guardian A against student B's path fails) and `tests/db/documents-read-actions.test.ts`/`documents-rls.test.ts` (guardian/student/teacher scoping).
- Upload to or overwrite a path not owned (upsert, token reuse, crafted pending rows over PostgREST): `tenant_docs_insert` requires an existing `pending` row with `created_by = caller` at the same path; no `storage.objects` UPDATE/DELETE policy exists, so re-upload/overwrite of an already-created object is denied by default-deny RLS; `documents_insert`'s `with check` ties `path` to the row's own `institution_id/entity_type/entity_id` and requires `created_by = app.current_user_id()`; `documentId` (and thus `path`) is always server-generated (`crypto.randomUUID()`), never client-supplied. Confirmed in `documents-acceptance.test.ts` (`directUpload` to `bypassPath` with no pending row fails).
- `documents` RLS vs the 07 §2.2 rows (admissions limited to student/application; staff own docs; guardian/student own child): matches `ROLE_PERMISSIONS` in `src/lib/auth/permissions.ts` and the `documents_select`/`documents_insert`/`documents_update` policies; exercised by `tests/db/documents-rls.test.ts` and the escalation fixture map (`tests/security/escalation.test.ts:159-165`, all 4 actions present).
- Guard trigger completeness: see MEDIUM finding above (status/identity columns covered; `deleted_at`/`deleted_by` are not). `service_role`/`postgres` bypass matches lesson 5 (role claim or `session_user`, never a null-uid special case).
- Polymorphic `entity_id` binding per `entity_type`: `student`/`staff`/`application` all cross-checked against their owning table + institution on insert; `submission` is the one gap, see LOW finding above.
- PII in audit/errors/logs: `audit()` calls in `actions.ts` pass only ids (`documentId`, `entityType`/`entityId` of the linked entity) as metadata — no `file_name`/`path` written to `audit_events`. `mapSqlError`/`logUnexpectedError` only put raw errors in server-side `console.error` (never returned to the client beyond a correlation id) — same pattern as the rest of the codebase, not specific to this diff.
- Signed-URL lifetime: read URLs expire in 60s (`READ_URL_EXPIRES_IN`); upload URLs use the SDK default; both generated via the caller's own session client, never service role.
- RLS performance (per-row definer calls): broad branches use the `(select app.my_institution_ids(...))`/`(select app.my_student_ids())` InitPlan pattern (lesson 7); the staff-ownership branch is a single-row `exists`, not a definer call. Consistent with other migrations; not re-audited at the helper-function level (pre-existing infra, out of this diff).
