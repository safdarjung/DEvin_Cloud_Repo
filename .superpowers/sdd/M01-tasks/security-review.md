# M01 HTTP dispatcher — security review

Scope: `.superpowers/sdd/M01-tasks/m01-diff.patch` (read once) — dispatcher
POST/GET routes, `all-actions.ts` manifest, `define-action.ts`/`registry.ts`
meta additions, `api-envelope.ts`, `withBearerToken` in `src/lib/supabase/server.ts`,
new tests. Read-only review, no edits made.

## Findings

src/app/api/v1/actions/[name]/route.ts:1, src/app/api/v1/actions/route.ts:1: MEDIUM: no rate limiting on the dispatcher. Every other cost/abuse-bearing route in the repo (src/app/api/public/enquiry/route.ts, src/app/api/ai/*/route.ts) applies a rate limiter; this generic dispatcher does not, despite making every current and future `defineAction` reachable over authenticated HTTP. It is also a scriptable oracle today: any authenticated user (any institution) gets 404 for "not a member/doesn't exist" vs 403 for "member, wrong permission" vs 401 "no/invalid token" on any institution slug, so unlimited requests let an attacker-with-any-account enumerate which institutions they belong to or probe permission boundaries at scale, something far cheaper via curl than via the previous UI-only surface. Fix: add the same rate-limit helper already used by `src/app/api/public/enquiry/route.ts` to both routes, keyed by caller (user id from claims, falling back to IP) + action name.

src/app/api/v1/actions/route.ts:17: LOW: GET listing doesn't call `isCrossSiteRequest` the way the POST dispatcher does (route.ts:50 in `[name]/route.ts`). Not exploitable today — no CORS headers are configured anywhere in the app (verified), so a cross-site page cannot read the JSON response, and the endpoint is read-only/non-tenant data (name + permission + JSON schema, no PII/secrets found in any registered schema's defaults). Flagging for consistency: if CORS is ever added for this listing (e.g. for a public API-docs page), the missing check becomes live. Fix: add the same `isCrossSiteRequest` guard for defense-in-depth parity with the POST route.

## Checked, no issue found

- **Bearer scope / AsyncLocalStorage leak across concurrent requests** (`src/lib/supabase/server.ts`): `withBearerToken` scopes via a dedicated `AsyncLocalStorage`; `createClient()`/`getClaims()` only read it when set, so every non-dispatcher caller (cookie-based Server Components/Actions) is unaffected. `tests/db/bearer-client.test.ts` ("scope does not leak after fn resolves") exercises this against the real ALS, not a mock.
- **React `cache()` (src/lib/auth/context.ts `getTenantContext`) + new bearer path**: this `cache()` usage pre-dates M01 and is already called from existing Route Handlers (`src/app/api/ai/quiz/route.ts` and siblings) with cookie auth, so Route-Handler-scoped `cache()` is an already-relied-upon pattern, not a new exposure from this diff. Next.js scopes React's `cache()` per request even in Route Handlers (its own request-store wraps Route Handler execution same as RSC render); the custom bearer-token ALS is a separate, additional store layered on top, not a replacement, so no cross-request mixing of institution/user context was found.
- **JWT verified, not just decoded**: traced `@supabase/supabase-js`'s `getClaims()` (minified `dist/umd/supabase.js`) — it decodes, enforces `exp` (unless `allowExpired`), then either does a real `crypto.subtle.verify` against the project's own `.well-known/jwks.json` key (RS/ES algs) or falls back to a network `getUser()` call to Supabase Auth (HS*/no-kid tokens) — never trusts the payload on signature alone. RLS at the Postgres/PostgREST layer independently re-verifies the same JWT, so even a bypass of the app-level check would still be blocked at the DB.
- **CSRF on cookie path**: `isCrossSiteRequest()` runs first in the POST dispatcher, before body read; bearer-authenticated calls are immune to CSRF by construction (browsers never auto-attach `Authorization` cross-site). `tests/db/api-actions-route.test.ts` has an explicit `Origin: https://evil.example -> 403` case.
- **Forged 3rd `overrideCtx` argument**: the dispatcher calls `action(slug, parsedBody.data.input)` — exactly two arguments, always. `overrideCtx` (the test-only bypass already gated on `process.env.VITEST` per the GU-09 comment in `define-action.ts`) is structurally unreachable from this route; nothing in the diff changes that gate.
- **Registry lookup with `__proto__`/`constructor`**: `registry`/`metaRegistry` in `src/lib/actions/registry.ts` are real `Map` instances, not plain objects, so `.get("__proto__")` is an ordinary (missing) key lookup — no prototype-chain fallthrough or pollution vector.
- **Error/PII leakage**: every response goes through `apiResponse`; the dispatcher's own catch-all returns only `internal` + a correlation id to the client, logging the real error server-side only (`console.error`). No stack traces, SQL, or raw Postgres errors reach the HTTP response.
- **Actions assuming browser/Server-Action context**: grepped all ten modules imported by `all-actions.ts` — none call `cookies()`/`redirect()`/`notFound()` directly; only the shared `getTenantContext` resolver does, and the dispatcher explicitly intercepts its `NEXT_REDIRECT`/`NEXT_HTTP_ERROR_FALLBACK;404` digests and maps them to 401/404 JSON instead of letting a framework control-flow exception escape as a 500. `revalidatePath`/`revalidateTag` calls in several action files are supported in Route Handlers by Next 16, so no functional break found either.
- **GET listing sensitivity**: requires authentication (claims check); exposes only `name`, `permission` (string already visible via the client-side permission matrix), and `z.toJSONSchema` structural output. Grepped all module schemas for `.default()` tied to `process.env`/secrets — none found.
