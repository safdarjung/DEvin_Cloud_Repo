## Findings (one line each)

- HIGH — supabase/migrations/20261028000083_online_payments.sql `record_online_payment` + src/app/api/public/payments/razorpay/route.ts — money captured at the gateway but `app.record_payment`'s outstanding check fails when the invoice was paid/reduced between intent and capture → webhook 400 `validation_failed`, no payment/ledger row, Razorpay retries then drops it; captured funds never reach the books. Fix: on `validation_failed` from `record_payment` inside the definer, mark the intent (`status = 'unreconciled'` or an audit `finance.payment.unreconciled` with order/payment ids) and return 200 so the event is not lost; add a `12-decision-log.md` debt row + a test "invoice paid between intent and capture".
- MEDIUM — supabase/migrations/20261028000074_finance_plus.sql `app.void_payment` lines 174-185 — idempotent fast path matches `(institution_id, idempotency_key)` only, never `payment_id`; a key reused for a different payment returns the other payment's reversal as `ok` and the second payment is silently never voided. Fix: add `and payment_id = p_payment_id` to the fast-path select and raise `code:conflict` when the key exists for another payment (same pattern for `create_payment_intent` vs `invoice_id`, see LOW below).
- MEDIUM — src/modules/finance/online-payments.actions.ts lines 80-90 + src/modules/finance/schemas.ts `CreatePaymentIntentSchema` — in test mode `createRazorpayOrder` runs before any invoice-state/outstanding check and `amount` has no upper bound, so any `finance.payment.online` holder (guardian) can create unbounded, arbitrary-amount Razorpay orders per request (orphan orders, gateway quota abuse). Fix: have `requireVisibleInvoice` select `status,total,paid_total`, reject `amount > outstanding` / non-open invoice with `validation_failed`/`invalid_state` before the gateway call; add `.max(10_000_000)` to the schema.
- MEDIUM — src/lib/actions/result.ts `mapSqlError` (ruling "Error codes": 42501/23505 must never surface as `internal`) — only `code:<x>` messages are mapped; SQLSTATE 42501/23505 become `internal` 500. Reachable in M12: `record_online_payment` when a provider payment id is replayed against a second order (`app.record_payment` idempotency returns the existing payment → `online_payment_intents.payment_id` unique → 23505 → 500 + correlation id); direct PostgREST writes to the three new tables → 42501. Fix: map `err.code === "42501"` → `forbidden`, `"23505"` → `conflict` in `mapSqlError` (shared file, lead edits) + unit test.
- LOW — supabase/migrations/20261028000083_online_payments.sql `create_payment_intent` lines 123-129 — idempotent fast path ignores `invoice_id`; key reuse for a different invoice returns the earlier intent (same institution, RLS-visible only). Fix: `and invoice_id = p_invoice_id` else `code:conflict`.
- LOW — src/modules/finance/razorpay.ts `RazorpayWebhookSchema.payload.payment.entity.amount` is `z.number()` not `.int()` — a non-integer amount reaches `p_amount_paise bigint` → cast error → 500 `internal` (no body logged; `mapSqlError` logs only the PostgREST error object). Fix: `z.number().int().nonnegative()` → 400.
- LOW — src/app/api/public/payments/razorpay/route.ts — no rate limit on a public POST (enquiry route has `rate_limited`); mitigated by HMAC before parse + 64 KB cap. Fix: reuse the enquiry route's limiter keyed by IP, or record as accepted (webhook IPs are Razorpay's).
- LOW — supabase/migrations/20261028000074_finance_plus.sql `app.void_payment` line 208-222 — `v_receipt` is read without a null check; a payment with no receipt row → `snapshot` null → 23502 → 500. Fix: `if v_receipt.id is null then raise 'code:invalid_state'`.
- LOW — src/modules/jobs/handlers/finance.fee_reminder.ts lines 100-107 — `memberships ... .maybeSingle()` with no unique on `guardian_id`: a guardian linked to two active guardian user accounts → PGRST116 → whole term job fails (same shape as notify.attendance_absence). Fix: `.limit(1)` + first row.
- LOW — src/modules/finance/reminders.actions.ts lines 49-50 — `asOf` recomputed in TS, not read from the RPC; at an institution-midnight boundary the returned `asOf` can differ from the job payload's. Fix: have `enqueue_fee_reminders` return `{jobId, asOf}` (migration is uncommitted, still editable) and pass it through.
- LOW — scripts/db-backup.ts line 122 — `--db-url <SUPABASE_DB_URL>` is passed on argv (password visible in `ps` to other local users while `supabase db dump` runs); stderr/throw paths are redacted via `redactDbUrl`, `manifest.json` carries host/port/db only, dump files chmod 0600 — no file/log leak found. Fix (optional): pass via `PGPASSWORD`/env or `--db-url` from a `.pgpass`, or accept as local-only.
- LOW — scripts/db-restore.ts lines 106-111 — error path prints `err.message` unredacted; postgres.js errors never embed the URL and `assertRestoreTarget` messages are URL-free, so no leak today; keep it that way (do not add `url.toString()` to messages).
- LOW — tests — missing for stated behaviors: concurrent double-void race (two keys, two connections, invoice lock), key reuse across payments/invoices, `refund` and `cheque_bounce` happy path (Cr `bank`), invoice paid between intent and capture (webhook outcome), non-integer webhook `amount`, 42501/23505 mapping, `payment.captured` with currency ≠ INR → ignored.
