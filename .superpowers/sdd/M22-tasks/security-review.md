Source: reviewer pass on M22 diff (lane-h). Findings written here first (reviewer is read-only), then fixed below.

## Findings (as received)

- **MEDIUM** `docs/planning/coolskool/12-decision-log.md`: new Debt register entries DBT-41..DBT-46 (added by M22-T12, lines ~304-309) reuse IDs already assigned to unrelated pre-existing debt rows (DBT-41 "Publish button renders for a role without permission", DBT-42 "no rate limit on /api/v1/actions", DBT-43 "page gates on wrong permission key", DBT-44 "CSV import scope", DBT-45 "infinite recursion in guardian_students RLS", DBT-46 "flaky invoice-generation test", at lines 410-415). The task brief said to use the "next free DBT rows", but the highest existing DBT number in the file is already 88 (per the recent M16 renumbering commit), so the new entries should have been DBT-89..94. This also inserts a second, duplicate "## 3. Debt register" heading ahead of the pre-existing "## 2. Phase 0 verified facts" / "## 3. Debt register" sections, breaking the document's section numbering. Fix: renumber the M22 entries to the real next-free IDs and fold them into the existing single Debt register table/section instead of a new duplicate heading.

- **MEDIUM** `docs/planning/coolskool/07-security-and-ai-governance.md`: the new §4 row for `src/modules/agents/service-role.ts` (M22) describes guard `app.guard_agent_run_update` as having "no bypass except `service_role` JWT claim or `session_user = 'postgres'`". The actual migration (`supabase/migrations/20261028000095_agents.sql`, function `app.guard_agent_run_update`) contains no such bypass check at all — its own header comment explicitly states "no service_role/postgres bypass (unlike this repo's other guards)" and the function body has zero branches for trusted callers; the state machine applies unconditionally to every UPDATE including service-role writes. The doc text contradicts the shipped code and could mislead a future reviewer/auditor about the guard's actual (stricter) behavior. Fix: correct the §4 row to say the guard has no bypass at all, matching the migration.

- **LOW** `src/modules/agents/queries.ts`: query handlers (`agentDefinitions`, `hydrateRuns`, `agentRuns`, `agentRunDetail`) `throw error`/`throw defError` directly instead of routing through `mapSqlError` the way `src/modules/agents/actions.ts` does. `guardedCall` in `define-action.ts` still catches and maps these to a generic `internal` envelope (so no raw SQL text leaks to the client), but a genuine `23505`/`42501` on these paths would surface as `internal` rather than the more specific `conflict`/`forbidden` mapping used elsewhere in the codebase for consistency. Low impact since these are read-only SELECT paths where such codes are unlikely to occur.

- **LOW** `supabase/migrations/20261028000095_agents.sql`: `agent_runs_rejected_decided_check` only requires `decided_by is not null` when `status = 'rejected'`, but does not also require `decided_at is not null` at the same constraint level (the guard trigger does enforce both together on the `awaiting_approval -> rejected` transition, so this is defense-in-depth only, not currently exploitable through the only write paths that exist).
