## Findings

| Severity | File | Issue + fix |
|---|---|---|
| MEDIUM | `supabase/migrations/20261028000077_scheduled_reports.sql` (`public.report_fee_defaulters`, lines ~427-431) | The `enrolments`/`class_sections`/`grades` left-join chain used to derive `grade`/`section` filters only on `e.student_id`/`e.academic_year_id`/`e.status`, with no explicit `e.institution_id = p_institution_id` (or `inv.institution_id`) predicate — unlike `app.term_attendance_percentage` (0009) and `report_attendance_daily`'s own `enrolled` subquery style, which the codebase's established "lesson" (0009 fix round 1) is to scope every lookup explicitly to the institution as defense in depth, not rely solely on upstream FK/UUID uniqueness. Not currently exploitable (student/invoice ids are globally-unique UUIDs tied 1:1 to an institution via FK, so no real cross-tenant row can match), but it diverges from the pattern the rest of the codebase follows for exactly this kind of join. Fix: add `and e.institution_id = inv.institution_id` to the `enrolments` join (and equivalent for the `class_sections`/`grades` joins if they don't already inherit scoping through `e`). |
| LOW | `supabase/migrations/20261028000077_scheduled_reports.sql` (`public.report_attendance_daily`, `enrolled` subquery ~lines 364-367) | Same pattern as above: `public.enrolments e where e.class_section_id = sections.class_section_id and e.status = 'active'` has no explicit `e.institution_id = p_institution_id`. `sections` is already institution-scoped so this is effectively safe (a `class_section_id` can only belong to one institution), but for consistency with the codebase's defense-in-depth convention, add the institution filter. |
| LOW | `docs/planning/coolskool/12-decision-log.md` (DBT-73) | Documented (not newly found) debt: `report_attendance_daily`/`report_fee_defaulters` are not gated by `app.module_enabled('scheduled_reports')`, so a direct `.rpc()` call bypasses the TS-layer module check that `report.export`'s `defineQuery({module: "scheduled_reports"})` enforces. Low risk in practice — the caller still needs `attendance.read`/`finance.read` and passes through normal RLS on the underlying tables, so no data is exposed that the same role couldn't already reach through other existing queries; this is purely a module-toggle consistency gap, already tracked by the milestone's own debt row. No action required beyond what DBT-73 already proposes. |
| LOW | `tests/db/report-queries.test.ts` ("teacher: forbidden on report.export regardless of source") | The test only exercises `source: "finance.defaulters"` for the teacher role via a direct `reportExport()` call (bypassing the `defineQuery` wrapper's `data.export` gate). Teacher actually holds `attendance.read` (scoped), so calling `reportExport` directly with `source: "attendance.daily"` would not throw at the handler's inner permission check — it is only blocked in the real HTTP path by the outer `data.export` gate in `report.export`'s `defineQuery`, which teacher lacks. Not exploitable via the real API (confirmed: `defineQuery`'s `permission: "data.export"` always runs before the handler), but the test name overstates coverage ("regardless of source") when the attendance.daily case isn't actually asserted at this unit-test layer. Cosmetic test-accuracy nit only.

## Verified correct (no issue)

- RLS on `scheduled_reports`: SELECT/INSERT/UPDATE restricted to `app.my_institution_ids(['owner','principal','admin'])`, no DELETE policy; write guard forces `created_by` for non-trusted callers and blocks `institution_id`/`created_by` mutation; cross-institution update-by-id correctly falls through to `not_found` at the action layer and would also be blocked by RLS even if the app-level filter were removed (defense in depth, confirmed via `tests/db/report-actions.test.ts`'s "another institution's schedule id" case and the RLS test's "admin of A inserting with B's institution_id" 42501 case).
- `documents_select_report` / `documents_report_guard`: restrictive guard's `with check (entity_type <> 'report')` makes it impossible for any non-service-role write to ever create/alter a `report` document row; recipient-role scoping via `app.my_report_ids()` matches the "narrower than 0067" ruling and is covered by `report-sources-rls.test.ts`'s attendance/finance recipient-isolation cases.
- `report.export`/`report.runs`/`report.list` (`src/modules/reports/queries.ts`) derive `institutionId` exclusively from `ctx.institution.id`, never from user input — no BOLA path into another institution's rows via the export RPC.
- `enqueue_due_reports`: `security definer`, `execute` revoked from `public/anon/authenticated`, granted only to `service_role`; payload built entirely from the locked row (not caller input); `for update skip locked` + idempotency key `report.generate:<id>:<fire-minute>` correctly prevents duplicate jobs across concurrent sweeps; module-off rows are left untouched and resume correctly when re-enabled (tested).
- `report.generate` handler re-reads the schedule and re-parses params at send time rather than trusting the sweep's payload beyond the two ids; skips cleanly on `paused`/missing; CSV injection guarded via `escapeFormula` (shared with `csv.ts`, behavior-preserving extraction); idempotent via deterministic storage path + `documents.path` unique constraint + `onConflict: "path", ignoreDuplicates: true`; notifications keyed per recipient so retries don't duplicate.
- `scheduled_reports_before_write`: trusted-caller detection via `nullif(current_setting('request.jwt.claims', true), '')::jsonb ->> 'role' = 'service_role'` (DBT-34-safe NULL handling) or `session_user = 'postgres'`; recipient-role allowlist + uniqueness enforced at the DB layer in addition to the Zod `.strict()`/`.refine()` checks in `src/modules/reports/schemas.ts` (defense in depth).
- `permissions.ts`: `report.schedule` → owner/principal/admin only; `data.export` → owner/principal/admin/accountant only; no other role (admissions, exam_controller, teacher, student, guardian) received either permission — matches 07 §2.2 exactly, confirmed by direct read of the merged role arrays (not just the diff hunks, which are easy to misread at block boundaries).
- `app.*` helper functions (`cron_field_match`, `cron_next_fire`, `report_source_roles`) are security invoker with execute revoked from public and no grant to `authenticated`; only callable from within the security-definer trigger/sweep functions that share the migration-runner owner, consistent with the codebase's established "lesson 5" pattern (confirmed against `tests/security/grants.test.ts`'s exhaustive `APP_AUTHENTICATED`/`PUBLIC_AUTHENTICATED` allowlists, which do not need updating since these three functions are never granted to `authenticated`/`anon`/`service_role`).
- `documents/schemas.ts` `ENTITY_TYPES`/`ALLOWED_MIMES` correctly left unchanged (users cannot request `entity_type: "report"` through `document.write`'s Zod schema even before the DB guard is reached — belt-and-suspenders).
- `PREFERENCE_CATEGORIES` in `announcements.schemas.ts` correctly NOT extended with `"report"` (in-app only, no preference-filtering needed), while `NotificationCategory` in `templates.ts` is extended — matches the ruling precisely.
- Jobs wiring (`registry.ts`, `types.ts`, `handlers/index.ts`, `runner.ts`): `report.generate` → module `scheduled_reports` in `JOB_MODULES`; `enqueueDueReports` port called exactly once before the claim loop, wrapped in try/catch with a correlation-id log, never blocking the claim loop (tested in `tests/unit/jobs-runner.test.ts`).
