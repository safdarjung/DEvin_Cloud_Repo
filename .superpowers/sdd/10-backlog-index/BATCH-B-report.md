## 6. Fix round 1 (review MED — non-transactional assignment/answer-key writes)

Problem: `createAssignment`/`updateAssignment` write `assignments` and `assignment_answer_keys` as two separate statements (§2 above's own documented shortcut). `publishAssignment` never checked the key existed, so a failure between the two writes (or a stale key left over from an earlier edit) could publish a live quiz with no, or an out-of-date, answer key — unrecoverable once published (results/marks-style immutability doesn't apply here, but "published" assignments aren't editable either, per the existing "only draft assignments can be edited/published" guard).

Fix (`src/modules/academics/assignments.actions.ts`, `publishAssignment`): now selects `content` alongside the existing columns; if `content.questions.length > 0`, reads `assignment_answer_keys.answers` for that assignment and requires its question count to equal the content's question count, else returns `validation_failed` — `"Answer key missing or out of date — re-save the draft"` — before the publish `UPDATE` runs. A non-quiz assignment (`content` null) is unaffected. Draft edits (`updateAssignment`) already re-upsert the key on every content change, so the teacher recovers by re-saving, no DB intervention needed.

TDD: new case in `tests/db/assignments.test.ts` — teacher creates a quiz assignment (key written normally), the key row is deleted directly as the raw `postgres` connection (simulating the two-write race's failure mode), `publishAssignment` → `validation_failed` with the exact message, assignment stays `draft`; `updateAssignment` with the same content re-upserts the key; `publishAssignment` → `ok`, assignment becomes `published`.

Ruling (no change made): LOW "staff-on-behalf recheck" stays as implemented — `requestRecheck`'s permission gate (`exam.recheck.request`) remains student/guardian only; the RPC's own `app.exam_write_roles()` branch (parity with the dropped RLS policy, used so the window test could isolate the window check from ownership) is unused by any current UI/action path and is not being removed, per the lead's explicit no-change ruling.
