## Bugs found and fixed during verification (not in the original implementation)

1. **Ledger check-constraint violation**: a literal 100% ews_rte concession on every head zeroes the whole invoice (`subtotal - concession_total = 0`), which `ledger_entries`' `(debit = 0) <> (credit = 0)` check rejects. Fixed by using 99%, not 100% (shortcut, documented in `finance.ts`; upgrade only if a demo scenario ever needs a literal ₹0 invoice — 05 §8.1 doesn't).
2. **Non-deterministic marks across reseeds**: `exams.ts` fetched `subject_assignments` with no `ORDER BY`; PostgREST doesn't guarantee row order, so the same rng() draws got reassigned to different (section, subject) pairs across reseeds, scrambling `results.total`/`grade`. Fixed by sorting `assignments` by `(classSectionId, subjectCode)` — both deterministic values — right after fetching.
3. **`seed-determinism.test.ts` itself was checking the wrong thing** for the new sections: it hashed `results.id`/`invoices.id`, but `app.apply_recheck_decision`'s v2 rows and every `app.generate_invoice` call use `gen_random_uuid()` for the new row (not a seed-deterministic id) — genuinely random every reseed, by the production functions' own design. Rewrote the exams/finance fingerprints to hash business fields only (`student_id`/`total`/`grade`/`version_no`; `admission_no`+`term.sequence`/`total`/`status`), matching 05 §8's actual contract ("same numbers", not "same arbitrary sequence label assigned to each student" — `generate_invoice`/`record_payment` are called over a concurrent pool for speed, so *which* student's call commits first, and therefore which `invoice_no` they get, is not itself deterministic; the totals/statuses are).

## Assumptions made
- **Finance structures (24, not 12)**: the packet's "Expected changes" bullet calls for "transport assigned to ≈40% of students," but `fee_assignments` is one-structure-per-student with no component override table — the only way to make transport genuinely optional per student is two structure variants per grade. Recorded here per CLAUDE.md's pre-code protocol instead of asking, since it's resolvable with a safe default.
- **ews_rte concession percent (99%, not 100%)**: see bug 1 above — a documented `shortcut` in `finance.ts`, upgrade only if a future demo scenario needs a literal ₹0 invoice (none does per 05 §8.1).
- **Admissions "Expected changes" vs. "Demo-data contract" numbers**: T-029's packet text has two different enquiry-stage/converted-count tables (`40 enquiries... converted 6` in "Expected changes" vs. `12/10/6/5/4/3` in the mandatory "Demo-data contract" section). Followed the Demo-data contract (CLAUDE.md rule 11: "demo-data contract from 05 §8.1 is a contract"), and reconciled the application count (8) so 4 come from the 4 converted enquiries and 4 are walk-ins (2 named + 2 generic), rather than the "6 converted + 2 walk-in" the Expected-changes bullet implied.
- **Exam `published_at`/invoice `created_at` are real timestamps, not the narrative business dates** ("published 2026-10-05") — `app.publish_exam_results`/`app.generate_invoice` stamp these with real `now()` internally (no parameter to override), same as every other operational-metadata column in the existing seed; only business dates (term boundaries, invoice `due_on`, exam `held_on`) are fixed 2026 calendar dates.
- Payment `received_at` is bounded to a safe window within each term (≤20 days into Term 2) so it never exceeds `app.record_payment`'s "not in the future" check regardless of the real wall-clock date this seed is run on.
